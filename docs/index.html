Chapter 01 · Orientation

Build the product, then build confidence in it.

This book follows TradeChart Lab from a clean clone to a tested Windows package, a signed Android APK, a GitHub release, and a public GitHub Pages guide. It uses the actual repository layout and scripts—every command has a place in the current project.

⌁ Desktop

C++20, Qt 6.8.3, WebEngine, and a locally vendored chart renderer.

◇ Android

Qt Quick, Android WebView, native TLS, and reproducible ARM64 packaging.

↗ Delivery

SSH Git operations, pull-request checks, release artifacts, and GitHub Pages.

What the application is

TradeChart Lab is an independent charting and research application. TradingView Lightweight Charts renders the visual chart, but it does not provide market data. The application requests Yahoo Finance first, can fall back to Twelve Data when a key is present, and uses deterministic demo data when neither provider succeeds.

Symbol requestTicker and interval
→
Yahoo Finance Primary polled sourceSuccess: use and label
If unavailable→
Twelve Data Optional configured fallbackSuccess: use and label
If unavailable→
Deterministic demo Offline-safe last resortNever presented as live

The first successful provider ends the chain. Every result keeps its source, timestamp, and demo/market status visible.

Keep the boundary clear

This is a research and paper-simulation tool. It does not connect to a broker, place orders, guarantee provider availability, or predict future returns. Historical tests describe past samples; they do not turn uncertainty into certainty.

Definition of done

  • The same source revision passes web, native, desktop smoke, and Android package checks.
  • The Windows ZIP includes Qt WebChannel, WebEngine, platform, SQL, network, and TLS runtime files.
  • The release APK is signed with the established key and verified before distribution.
  • The commit is reviewable, pushed through the configured SSH remote, and protected by CI.
  • The public book URL serves exactly the content that was merged to main.
Chapter 02 · The route

A detailed delivery plan

Treat delivery as a sequence of evidence gates. A phase is complete only when its output is both created and checked.

1

Discover

Read the repository, confirm the active branch and SSH remote, identify platform boundaries, and inventory existing tests and workflows.

Gate: no assumptions contradict source or automation.
2

Design

Define user outcome, data flow, platform scope, error states, persistence, security boundaries, and measurable acceptance criteria.

Gate: the plan says what will not be built as clearly as what will.
3

Implement

Keep domain logic independent from widgets where possible; make desktop and Android adapters explicit; update tests with behavior.

Gate: code compiles and expected behavior is observable.
4

Review

Inspect correctness, lookahead bias, input bounds, ownership, failure recovery, layout, provider provenance, and package contents.

Gate: discovered issues are fixed or intentionally documented.
5

Package

Run the same tested scripts used by CI. Produce immutable artifacts and SHA-256 checksums; never distribute a raw desktop executable.

Gate: the staged package starts without the developer Qt environment.
6

Publish

Commit a focused diff, push over SSH, review in a pull request, require passing checks, merge, create the release, then verify public downloads and Pages.

Gate: a clean machine or public browser can consume the output.

Plan template for a new phase

  1. Outcome: one sentence describing the user-visible result.
  2. Scope: desktop, Android, shared model, data source, persistence, and UI.
  3. Non-goals: related behavior deliberately excluded.
  4. Risks: data licensing, no-lookahead correctness, security, performance, and migration.
  5. Implementation: files, ownership boundaries, state transitions, and failure paths.
  6. Verification: unit, integration, package, visual, and workflow checks.
  7. Delivery: branch, commit, PR, merge, artifacts, documentation, and rollback.

Review the plan before writing code

Challenge each dependency and transition: where does the value come from; how old may it be; what happens when it is missing; can future information leak into a historical calculation; does Android really implement the same feature; and what will a user see when a provider refuses the request? Convert each answer into a test or visible status.

Useful rule

A plan item such as “add analysis” is not executable. “Compute the metric from completed bars, exclude the selected bar’s future, display sample size and source timestamp, and test the first valid index” is.

Design boundaries worth preserving

BoundaryWhy it existsReview question
Renderer ≠ data providerLightweight Charts draws values but supplies none. Is every displayed value sourced and freshness-labelled?
Raw cache ≠ adjusted viewCorporate-action bases can be reproduced without corrupting source bars. Did this change preserve raw stored observations?

Runtime dependency chain

The desktop executable embeds a web page through Qt WebEngine and communicates through Qt WebChannel. That is why copying only tradingview_chart.exe fails on another machine. The packaging script runs windeployqt, checks critical DLLs and resources, then launches a smoke test from the staged directory with a restricted PATH.

Chapter 04 · Setup

Prepare a reproducible workspace

Start from known tools and a clean source state. Local build directories, SDKs, keys, databases, and API secrets are not source code and must stay outside commits.

Prerequisites

Git + GitHub SSHClone and push without embedding credentials.
Visual Studio 2022Desktop C++ workload and MSVC x64.
PowerShell 7Run the repository packaging scripts.
Python 3Install Qt kits through pinned aqtinstall.
Node.js 22+Verify and refresh the vendored chart dependency.
Android Studio toolsOnly required for local APK builds.

Clone with the existing SSH identity

Set-Location (Join-Path $env:USERPROFILE 'source\repos')
git clone git@github.com:buicongnguyen/tradingview_chart.git
Set-Location .\tradingview_chart
git remote -v
git status --short --branch

The expected fetch and push URL is git@github.com:buicongnguyen/tradingview_chart.git. If an existing clone uses HTTPS, switch only this repository:

git remote set-url origin git@github.com:buicongnguyen/tradingview_chart.git
ssh -T git@github.com

Verify the web dependency

npm ci
npm run sync-web-deps
npm run test:web
git diff --exit-code

npm ci uses the lock file. The synchronization command copies the pinned Lightweight Charts 5.2.0 bundle and required notices into the local renderer assets. A clean diff proves committed vendor files already match the dependency declaration.

Configure provider identities without committing secrets

# Optional market-data fallback
$env:TWELVE_DATA_API_KEY = 'session-only-value'

# Optional research provider
$env:ALPHA_VANTAGE_API_KEY = 'session-only-value'

# Required identity for manual SEC requests
$env:SEC_USER_AGENT = 'TradeChartLab personal research your-email@example.com'

# Optional FRED event import
$env:FRED_API_KEY = 'session-only-value'
Never place real values in source, examples, logs, or screenshots

Environment variables above are process-scoped examples. The Android signing key and password also stay outside Git. Losing the established signing key prevents an installed Android app from accepting future upgrades under the same identity.

One-time Qt bootstrap

pwsh -NoProfile -File .\scripts\bootstrap-qt.ps1

The script installs Qt 6.8.3 under .qt with WebEngine, WebChannel, and Positioning. It uses a repository-local Python environment and verifies the required CMake modules before succeeding.

Developer build

pwsh -NoProfile -File .\scripts\configure-windows.ps1 -Configuration Release

$cmake = 'C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe'
& $cmake --build .\build-release --config Release --parallel
ctest --test-dir .\build-release -C Release --output-on-failure

Run from the build tree

$qtRoot = (Resolve-Path .\.qt\6.8.3\msvc2022_64).Path
$env:PATH = "$qtRoot\bin;$env:PATH"
.\build-release\Release\tradingview_chart.exe
Why the Qt6WebChannel.dll error appears

The raw executable resolves Qt libraries from PATH. For normal use, run the executable inside dist\TradeChartLab-1.2.0-win64 after packaging. Do not solve deployment by manually copying one DLL—the application needs a complete, mutually compatible Qt runtime and WebEngine resources.

Create the self-contained package

pwsh -NoProfile -File .\scripts\package-windows.ps1

This command configures and builds Release, runs all native tests, stages licenses, invokes windeployqt, asserts critical runtime files, smoke-tests the staged app with a restricted environment, and creates:

  • dist\TradeChartLab-1.2.0-win64.zip
  • dist\TradeChartLab-1.2.0-win64.zip.sha256

Manual acceptance pass

  • Extract the ZIP to a new directory and start the packaged executable.
  • Load Yahoo data, then test offline demo and a valid local CSV.
  • Switch Basic, Intermediate, and Advanced workspaces and reset the layout.
  • Resize docks at 100%, 125%, and 150% display scaling; verify text does not overlap.
  • Open chart style, scale, indicators, research, strategy, and simulation flows.
  • Close and reopen to verify safe settings and persistence restoration.
Chapter 06 · Mobile

Build and sign the Android APK

Android shares the validated data and chart concepts, but uses its own Qt Quick presentation and Android-native network bridge. Desktop docks, multi-chart workspaces, and tray alerts are intentionally not claimed as mobile features.

Both meet only at signing↓
Sign APK Canonical application identity
→

→

CI path: build → inspect permissions and contents → publish a clearly labelled unsigned APK. No signing secret crosses that boundary.

Prepare the toolchain

Install Android Studio command-line tools and JDK 17 or newer. The expected default SDK location is %LOCALAPPDATA%\Android\Sdk. Then run:

pwsh -NoProfile -File .\scripts\bootstrap-android.ps1

The script verifies or installs Android platform 36, build tools 36.0.0, NDK 26.1.10909125, platform tools, and the Qt 6.8.3 ARM64 kit with Qt WebView.

Protect the application identity

The canonical key directory is %LOCALAPPDATA%\TradingViewChart\signing. Initialize it only once for a brand new application identity:

pwsh -NoProfile -File .\scripts\package-android.ps1 -InitializeSigningKey
Back up the entire signing directory securely

Do not commit it, upload it as an Actions artifact, or create a replacement when one part is missing. Android requires future upgrades to use the same key.

Create the release APK

pwsh -NoProfile -File .\scripts\package-android.ps1

The script builds ARM64 Release, signs with the established local material, verifies the certificate, and writes the APK and checksum under dist. For disposable CI output only:

pwsh -NoProfile -File .\scripts\package-android.ps1 -SkipSigning

Device acceptance pass

  1. Install: remove only an incompatible test build if necessary, then install the canonical APK on an Android 9+ ARM64 phone.
  2. Launch: confirm AAPL requests Yahoo; confirm failure visibly falls back to deterministic demo data.
  3. Interact: change symbol, timeframe, chart style, indicator, and provider fallback; use pinch and crosshair gestures.
  4. Rotate: verify portrait controls and the landscape chart-first layout.
  5. Constrain: test airplane mode, background/resume, slow network, invalid symbol, and invalid Twelve Data key.
  6. Read: verify text is legible at system font scaling and overlays remain opt-in on a small display.

What CI proves—and what it cannot

The Android workflow compiles the ARM64 package, checks the manifest for Internet access and absence of unexpected sensitive permissions, verifies the vendored renderer, and uploads an unsigned artifact. Only a physical-device pass can prove WebView behavior, rotation, touch interaction, OEM TLS/network differences, and real-world readability.

Chapter 07 · Evidence

Test behavior, then review the logic

Compilation catches syntax and type errors. It does not catch misleading finance semantics, lookahead, incomplete packages, stale UI state, or unreadable layouts.

The verification pyramid

Manual acceptanceReal workflows, displays, phones, networks
Package smokeRuntime dependencies and clean-environment launch
IntegrationParsers, storage, bridges, workflows
Unit and asset testsMath, bounds, state machines, vendored files
Static reviewOwnership, inputs, errors, provenance, scope

Run the automated suites

npm ci
npm run sync-web-deps
npm run test:web

pwsh -NoProfile -File .\scripts\configure-windows.ps1 -Configuration Release
cmake --build .\build-release --config Release --parallel
ctest --test-dir .\build-release -C Release --output-on-failure

Finance-logic review

QuestionFailure it prevents
Does a historical decision use only information available at that timestamp? Lookahead and survivorship-style overstatement.
Are warm-up, missing, rejected, and non-finite values explicit? Invented values and silent NaN propagation.
Are fills consistently next-open with configured cost assumptions? Impossible same-bar execution and inflated backtests.
Are sample size, baseline, interval, and coverage shown with an “accuracy” claim? False precision from a favorable hit rate.
Are currency, units, price basis, provider, and retrieval time preserved? Invalid comparisons and ambiguous displayed numbers.
Does simulation remain local, long-only, and non-broker-connected? Unexpected financial action.

Code review

  • Inputs are bounded before allocation, parsing, serialization, or iteration.
  • Asynchronous callbacks cannot use deleted objects or overwrite a newer request.
  • Files and databases are written atomically or recover safely from partial state.
  • User-facing errors name the failed operation and preserve usable previous data.
  • Tests cover first valid index, empty/one-item input, upper bounds, malformed input, and deterministic repeats.
  • Desktop-only and Android-only behavior is guarded and documented honestly.
  • Licenses and TradingView attribution remain in packaged output.

UI review

Test minimum supported window size, long translated/provider strings, system font scaling, dense tables, and restored settings from older versions. Prefer scroll areas, elision with tooltips, minimum useful dock widths, and task-based workspaces over forcing every panel onto the screen. Basic should answer “what is happening?”; Intermediate adds “why?”; Advanced adds modeling and strategy work.

Chapter 08 · Source control

Make the change reviewable

A good commit is a coherent statement: the diff, tests, documentation, and commit message all describe the same outcome.

→

→

→

Start from current main

git switch main
git pull --ff-only origin main
git switch -c codex/short-description
git status --short --branch

Inspect before staging

git diff --check
git diff --stat
git diff
git status --short

Do not stage local build trees, dist, databases, log files, API keys, Android signing material, IDE state, or unrelated user changes. Use explicit paths when the worktree contains more than the intended change.

Commit and push through SSH

git add docs .github/workflows/pages.yml tests/web/book_site.test.mjs README.md
git diff --cached --check
git diff --cached --stat
git commit -m "Add project book and Pages deployment"
git push --set-upstream origin codex/short-description

Open the pull request

gh pr create --draft `
  --base main `
  --head codex/short-description `
  --title "Add project book and Pages deployment" `
  --body "Summary, verification, risks, and deployment notes"

Keep it draft while checks or review work remain. The pull request should state:

  • the user outcome and files changed;
  • commands actually run and their results;
  • platform behavior not manually verified;
  • data, security, license, migration, or deployment risks;
  • the expected release or Pages URL after merge.
SSH and GitHub CLI are separate concerns

git push uses the repository’s SSH remote. The gh command uses its authenticated API token to create pull requests, inspect workflows, and manage releases. No remote URL conversion is needed.

Chapter 09 · Automation

Let GitHub reproduce the evidence

The repository runs independent Windows, Android, and Pages workflows. A green badge means that exact revision passed the scripted gates—not that every manual device or financial-semantic check has been performed.

One revision, three evidence lanes

Same commit SHA Pull request or trusted main revision
↓ fan out without changing source ↓
Windows Web integrity → Qt build → tests → deploy → smoke ZIP + SHA-256
Android Web integrity → Qt/NDK build → manifest and APK checks Unsigned APK + SHA-256
Pages Book integrity → docs artifact → protected environment Deploy only from main
Evidence gate Merge or release only when the required result for that exact revision passes.

Windows workflow

  1. Checkout source and install Node.js and Python.
  2. Synchronize and test the vendored renderer, then require a clean diff.
  3. Install Qt 6.8.3 for MSVC 2022 with required modules.
  4. Run scripts/package-windows.ps1 to build, test, deploy, and smoke-check.
  5. Upload the ZIP and SHA-256 sidecar as workflow artifacts.

Android workflow

  1. Verify the same web renderer inputs.
  2. Install host Qt, Android Qt, JDK 17, SDK platform/build tools, and pinned NDK.
  3. Cross-compile the ARM64 Release APK.
  4. Inspect permissions and APK contents.
  5. Upload a clearly labelled unsigned APK and checksum.

Pages workflow

  1. Run book integrity tests for local assets, chapter targets, navigation order, workflow scope, and unsafe accidental secrets.
  2. On pull requests, stop after validation.
  3. On main, upload only docs as the Pages artifact.
  4. Deploy that artifact to the protected github-pages environment.

Inspect checks from the command line

gh pr checks --watch
gh run list --limit 10
gh run view RUN_ID --log-failed

When a job fails, find the first meaningful error, reproduce the same command locally, fix the underlying source or script, rerun the relevant full gate, and push a new commit. Do not mask a deterministic failure with retries.

Workflow security

Keep default permissions read-only, then grant pages: write and id-token: write only to the deploy job. Pull requests must never receive signing keys. Pin tool versions where reproducibility matters, use official actions, and treat workflow logs and artifacts as public for this public repository.

Chapter 10 · Distribution

Publish installable application artifacts

GitHub Pages publishes documentation. GitHub Releases publishes the Windows package and Android APK. Keep those responsibilities separate.

Distribution map

Tested, tagged main commit One immutable source revision
↓ publish by responsibility ↓
Windows Portable ZIP + SHA-256GitHub Release
Android Signed ARM64 APK + SHA-256GitHub Release
Project book Validated docs directoryGitHub Pages

Verify every channel from a signed-out or private browser. A successful upload is not proof that a public consumer can install or read it.

Pre-release gate

  • The version agrees in package.json, artifact names, workflows, and user documentation.
  • Windows and Android workflows passed on the commit to be tagged.
  • The local signed APK certificate was verified and the key is backed up.
  • ZIP and APK SHA-256 files match their final bytes.
  • Third-party notices, licenses, and TradingView attribution are present.
  • Release notes distinguish real data, delayed/polled data, and deterministic demo data.

Tag and create the release

git switch main
git pull --ff-only origin main
git tag -a v1.2.0 -m "TradeChart Lab 1.2.0"
git push origin v1.2.0

gh release create v1.2.0 `
  .\dist\TradeChartLab-1.2.0-win64.zip `
  .\dist\TradeChartLab-1.2.0-win64.zip.sha256 `
  .\dist\TradeChartLab-1.2.0-android-arm64-v8a.apk `
  .\dist\TradeChartLab-1.2.0-android-arm64-v8a.apk.sha256 `
  --title "TradeChart Lab 1.2.0" `
  --notes-file .\RELEASE_NOTES.md

Replace the example version for the next release. Never move an existing public tag to a different commit; create a new patch version when shipped bytes change.

Verify from the public side

  1. Open the release while signed out or in a private browser.
  2. Download both platform artifacts and checksum sidecars.
  3. Compute local SHA-256 and compare exact lowercase/uppercase-insensitive hex.
  4. Extract Windows into a new folder and run it without the development Qt path.
  5. Install the APK as an upgrade on a device that has the previous signed release.

Rollback model

Do not delete evidence silently. If a release is unsafe, mark it clearly, describe the issue, retain or remove assets according to impact, fix forward on a new branch, and publish a new version. GitHub Pages can be restored by reverting the bad documentation commit and letting the Pages workflow redeploy main.

Chapter 12 · Maintenance

Keep the app and book trustworthy

A release is a checkpoint, not the end. Provider behavior, upstream dependencies, Android requirements, market semantics, and user workflows continue to change.

Troubleshooting map

Windows reports a missing Qt DLL

Run the packaged executable from the extracted dist folder. Rebuild with scripts/package-windows.ps1 if the folder was assembled manually. One copied DLL cannot replace WebEngine resources, plugins, and matching runtime libraries.

The chart shows demo values instead of real market data

Read the visible source label. Yahoo may be unavailable or rate-limited; Twelve Data requires a valid key and plan entitlement. Demo data is deterministic and explicitly labelled. Lightweight Charts itself never retrieves quotes.

The Android APK will not install as an upgrade

Confirm application ID, version code, device ABI, minimum Android level, and signing certificate. An APK signed with a different key cannot upgrade the installed app.

A historical theory reports high accuracy

Inspect sample size, Wilson interval, holdout result, unconditional baseline, excess return, event overlap, costs, and regime coverage. A hit rate alone is not a forecast or a reason to buy.

The GitHub Pages workflow fails

Run npm run test:web, inspect the first failed assertion, verify Pages is enabled with Actions as its source, and confirm deploy-job permissions and the github-pages environment.

Dependency update rhythm

  1. Read official release notes and security advisories for Qt, Lightweight Charts, Node, Android SDK/NDK, and GitHub Actions.
  2. Update one dependency boundary at a time on a branch.
  3. Regenerate pinned assets or lock files with the repository command.
  4. Run native, web, Windows package, Android package, and license checks.
  5. Document user-visible or toolchain changes in both README and this book.

Book maintenance checklist

  • Commands still match script names, parameters, paths, and versions.
  • Platform capability descriptions match current code.
  • Artifact names and release examples use the supported version.
  • Provider descriptions distinguish official, unofficial, free-plan, and manual sources.
  • New workflows and required permissions appear in the delivery chapters.
  • Every new chapter is represented in navigation, search, tests, continuous order, and scroll-spy tracking.
